# 11. 事件驅動回測 (Event-Driven Backtesting)

當我們確認了 Baseline 有基本的預測能力後，我們必須把程式升級為 **事件驅動回測 (Event-Driven Backtest)**。這是高頻交易中最接近真實世界的模擬方式。

## 1. 什麼是事件驅動？
在傳統的日線級別股票回測中（如 Backtrader），我們通常使用 `for` 迴圈跑過每一天：「如果今天開盤價大於某個值，我就買在收盤價」。這叫做 **Vectorized Backtesting (向量化回測)**。

但在微秒級別的微觀結構中這是不行的。你的掛單 (Quote) 會進入交易所的排隊隊伍中 (Queue)，你不知道什麼時候會成交。
**事件驅動**的架構是一步一步 (Tick by Tick) 推演的：
1.  **事件發生**：交易所送來一筆全新的委託簿快照 (LOB Snapshot) 或成交紀錄 (Trade Tape)。
2.  **狀態更新**：系統更新當前的 `bid` 價格與 `ask` 價格。
3.  **掛單處理**：系統檢查你自己掛在簿子上的單，「剛剛這筆真實市場的成交，有沒有吃到我的單？」
4.  **策略決策**：根據 TCN 最新的分數，決定是要**新增掛單、刪除掛單 (Cancel) 還是等待**。

這是一個嚴密的循環，絕不容許你看著未來的價格去成交現在的單。

## 2. 模擬排隊隊伍 (Queue-Aware Fill)
在回測 HFT 造市商策略時，最難的一點是**模擬你的被動單 (Passive Order) 什麼時候會成交**。
*   假設市場最佳買價 (Best Bid) 在 100.0，排隊的總量有 50 口。
*   你的機器人決定也在 100.0 掛買單 1 口。這時你排在第 51 名 (Queue Ahead = 50)。
*   接下來真實市場在 100.0 成交了 10 口。此時你還是沒成交，因為你前面還有 40 口。
*   一直到真實市場在 100.0 總共成交了 51 口以上，回測引擎才會判定：「你的這筆買單被真實成交了 (Filled)！」

這叫做 **保守填單估算 (Conservative Passive Fill)**。如果你的回測沒有模擬這種「排隊延遲」，你的 PnL 將會是極度失真的暴利，因為你以為你「一掛單就成交了」，這在現實中是不可能的。

## 3. 持倉 (Inventory) 與標記到市價 (Mark-to-Market Exit)
我們不希望神經網路一直買買買，累積了幾百口的單子爆倉。
所以在 Event-Driven 回測中，我們必須引入 **Inventory State (庫存狀態)**：
*   **最大持倉限制 (`max_inventory` = 2)**：最多只能拿 2 口多單或空單。滿了就不去掛買/賣單。
*   **標記到市價退出 (Mark-to-Market)**：如果持倉時間超過設定的最大忍受步數 (e.g., 20 ticks)，或是停損點到了，回測引擎會強制用「市價大單 (Market Order)」平倉。這意味著作多時，你必須砸在對面的 `Best Bid` 上，這會吃掉你整整 1 個甚至 2 個 tick 的滑價成本。

**總結**：Event-Driven 是最殘酷的照妖鏡。很多在 Baseline 看起來賺幾千 ticks 的策略，在 Event-Driven 排隊機制的洗禮下，獲利會瞬間歸零甚至大虧。這才是真實的高頻世界。

## ps. 第一階段回測的內容
1. 排隊延遲與撮合物理學 (Queue-Aware Fill)
*   模擬了什麼：它模擬了您的限價單被送到交易所後，必須在 LOB (限價委託簿) 裡面排隊等飯吃的過程。
*   機制：當您掛單在最佳買價 (Best Bid) 時，系統會抓取當下畫面上原本就有的掛單總量，以此設定為您的 queue_ahead (前方排隊人數)。接下來的每一個毫秒，只有當市場上出現真實的「主動砸盤單 (Taker Sell)」敲在您的價位上時，才會扣減您的排隊人數。必須等到前面的人都被買光，系統才會判定您的單子「真實成交」。徹底粉碎了傳統量化的「假性成交 (Illusionary Fill)」盲區。
2. 硬體與網路的傳輸延遲 (Network & Processing Latency)
*   模擬了什麼：透過參數 latency_steps = 0, 1, 2, 4，它模擬了訊號從「被大腦 (TCN) 算出」到「封包飛到交易所撮合引擎」之間的時間差。
*   機制：這正是專題的核心。delay=0 完美模擬了 FPGA 晶片在網路卡底層直接硬體決策的零延遲境界；而 delay=4 則模擬了 Python 軟體運行、作業系統 Context Switch 加上網路線傳輸的卡頓。
3. 被大單砸穿的逆向選擇 (Adverse Selection)
*   模擬了什麼：模擬了「為什麼造市商會虧大錢」的本質。
*   機制：這結合了上述的 1 加上 2。當外資大戶發動突襲 (毒性流量湧現)，如果系統延遲為 delay=4，即使您的 TCN 模型神機妙算發出了撤單指令，但因為封包還在半路上，大戶的主動單已經砸穿了 LOB，強制把籌碼塞給您，害您一建倉就面臨數十點的虧損。這完美還原了高頻交易中最可怕的 Adverse Selection 物理法則。
4. 零延遲緊急撤單 (Smart Canceling / Toxicity Freeze)
*   模擬了什麼：模擬了 FPGA 造市商專屬的「閃躲技能」。
*   機制：當 TCN 分數突破警戒值 (alpha_freeze_threshold)，引擎會觸發 action: freeze。這模擬了 FPGA 不計一切代價，在奈秒級別向交易所發出 Withdraw 封包，把 LOB 上雙邊的掛單瞬間抽走的極限防禦機制。
5. 持倉的未實現損益與流動性退場 (Mark-to-Market Exit)
*   模擬了什麼：模擬了手上拿著部位時，隨時可能被點差 (Spread) 吃掉利潤的現實。
*   機制：當您持有 1 口多單 (Long) 想平倉時，引擎不是用中間價 (Mid-price) 幫您平倉，而是嚴格採用當下的最佳買價 (Best Bid) 來算給您看（也就是讓您承受吃對手價的滑價損失）。它並全程動態模擬了您的嚴格停損 (stop_loss_ticks)、停利 (take_profit_ticks) 與不想抱單過夜的超時保護 (max_holding_steps)。
6. 庫存傾斜恐懼與動態報價 (Inventory Penalty & Dynamic Spread)
*   模擬了什麼：造市商最怕手上累積單一方向的部位（例如抱了滿滿的多單但市場正在跌）。
*   機制：當庫存越來越不平衡時，引擎會自動產生 inventory_penalty。這會讓模型主動「降價賤賣」手上的多單，並且「把買價掛得極遠」拒絕再接新單，完全重現了華爾街真實造市商 (Market Maker) 每天在做的避險行為。

## ps. 第一階段回測的限制

1. 市場衝擊完全為零 (Zero Market Impact)
*  回測中的運作：在我們的程式碼中，無論我們掛出多少口單、撤銷多少口單，歷史 LOB (限價委託簿) 的數據都是固定的，其他參與者就像瞎子一樣照常交易。
*   真實世界的殘酷：HFT 市場是高度對抗的「暗黑森林」。如果我們的 FPGA 機器人常態性地掛單與光速撤單，其他的 HFT 造市商（如 Citadel, Jump Trading）的演算法會立刻偵測到我們的存在。他們可能會針對我們的模型使用「誘捕單 (Spoofing)」，假裝放出毒性流量逼我們的 TCN 撤單，藉此消耗我們的運算資源或尋找我們策略的漏洞。我們的回測無法模擬這種「對手盤的反擊」。
2. 簡化的撮合隊列機制 (Approximated Queue Priority)
*   回測中的運作：我們抓取 bid_vol_1 當作 queue_ahead，然後逐筆扣除對向敲進來的 Taker 單，直到扣除完畢就當作成交。
*   真實世界的殘酷：真實交易所使用的是極度精密的 Price-Time Priority (價格時間優先) 或 Pro-Rata (按比例分配) 撮合引擎。真實世界裡有**「冰山委託 (Iceberg Orders / Hidden Liquidity)」**，你看到的報價深度 100 口，其實水面下藏了 1000 口。這些隱藏單會破壞我們的 queue_ahead 計算，導致我們的預期排隊時間嚴重失準。

3. 延遲的固定化 (Deterministic Latency vs. Jitter)
*   回測中的運作：我們用變數設定了 latency_steps = 0 或是 delay=4，這是一個固定的物理常數。一旦設定我們比別人快 4 個 Tick，整場回測我們就永遠比別人快。
真實世界的殘酷：現實中的網路封包與軟硬體處理有極高的隨機抖動 (Network Jitter)。在市場波動最劇烈、最需要 FPGA 保命的那個瞬間，交易所的 API Gateway 會因為全球塞滿了百萬筆封包而導致大塞車。即使你是 FPGA 發出的光速封包，也可能因為交易所路由器排隊而延遲。固定延遲無法模擬這種「微秒級的塞車意外」。

4. 忽略了手續費與造市返佣 (Fees & Maker Rebates)
回測中的運作：我們計算的 PnL 純粹是靠「賺取點差 (Spread)」減去「逆向選擇損失」。
真實世界的殘酷：高頻造市商真正的獲利來源，很大一部分其實是交易所給予的流動性提供獎勵 (Maker Rebate)。由於我們掛限價單提供流動性，交易所不僅不收手續費，反而會退錢給我們。另一方面，如果我們被迫用市價單逃跑，將會支付極高的 Taker Fee。把手續費結構加入計算後，整體利潤曲線會完全不同。

5. 主機代管與物理距離 (Colocation & Speed of Light)
回測中的運作：我們的資料是歷史整理好的，假設我們對所有資訊的接收都是完美的同步。
真實世界的殘酷：如果我們觀察台指期 (台北機房) 來做市，那沒問題；但加入 CME 後，就算你的 FPGA 寫得再好，你的伺服器如果沒有花天價租用 CME 位於美國伊利諾州的 Aurora 資料中心 (Colocation)，光信號透過跨洋海底電纜傳送也需要幾十毫秒。物理距離的限制將直接摧毀 FPGA 省下來的奈秒級優勢。

目前最大的限制在於它假設了 Market Impact (市場衝擊) 是零，且我們的排隊演算法無法預測冰山委託單。

但這並不損害我們本專題的結論。因為第一性原理的核心在於*『證明相對的硬體反應速度優勢能降低逆向選擇損失』**。我們在相同的假定環境下，利用相對的 delay=0 對抗 delay=4（圖表對照），已經足以證明這套 TCN 毒性撤單機制部署在 FPGA 上的純邏輯優勢。為了更貼近殘酷的現實，我們在下個階段導入真實 CME 數據與 C++ 驗證後，將會納入對手盤反應與手續費模型。
