# 15. 延遲證明基準測試 (Latency Proof Benchmark)

本專案的最核心目標，是向世界證明：「將高頻交易策略放到 FPGA 上執行，到底能產生多大的商業價值？」

為了給出這個證明，我們不是去買一塊昂貴的 FPGA 板子來跑。我們要在軟體回測中，搭建一個 **Latency Proof Framework (延遲證明框架)**。

## 1. 什麼是延遲敏感度對照？
在這個框架中，我們在 `hybrid_market_maker.py` 中加入了一個參數：`delay_steps` (延遲步數)。
這個參數代表著：當你的 TCN 預測到危險，並發出「撤單 (Cancel)」或「報價 (Quote)」指令後，這個指令要等幾個 ticks 才會真正到達交易所並生效。

*   **`delay = 0`**：代表無限快的極限速度。這模擬了 **FPGA** 將邏輯燒錄在硬體電路上，以奈秒(nanoseconds)級別完成推論與網路傳輸。
*   **`delay = 1`**：代表極度最佳化的 C++ 系統與高階網卡 (Kernel Bypass)。
*   **`delay = 2 到 4`**：代表軟體堆疊造成的延遲，像是 Python 直譯器、作業系統 Context Switch、一般網卡傳輸等。

## 2. 完美的證明劇本 (The Proof Goal)
我們要如何證明 FPGA 有價值？
我們要把同一組寫好的 TCN 與造市商邏輯 (Strategy Config)，丟進測試資料集 (Test Set) 裡，連續跑 4 次不同的延遲。

一個完美的證明劇本必須長這樣：
*   在 `delay = 0` 時：PnL (盈虧) 是深綠色的正數。因為機器人總能在毒性大單砸下來的前一秒，完美抽單！
*   在 `delay = 1` 時：PnL 是稍微盈利或打平。機器人偶爾被砸中，但勉強苟活。
*   在 `delay = 4` 時：PnL 變成深紅色的負數。因為撤單封包卡在網路上，無數次被大單無情碾壓，產生極大的逆向選擇損失 (Adverse Selection)。

## 3. 面臨的實戰困難與轉向
在早期的掃描中，我們發現策略如果設定得「太害怕虧損 (Quote-off Threshold 設太高)」，當 `delay=4` 時，機器人並不會虧大錢，因為它直接選擇**「我不玩了 (0 trades)」**。
用逃避來止血，無法凸顯速度的價值。

因此，我們將策略調整為 **無腦報價 (Dumb Quoting) + 第一性原理雷達撤單**：
強迫機器人在 `delay=0` 與 `delay=4` 時都勇敢地把單掛出去賺點差。唯一的差別在於「誰跑得快」。
一旦我們完成這個設定，我們就能產出這張 **單調向下遞減的 PnL 對照圖 (The Killer Chart)**，作為專題或論文中最棒的 Benchmark！
