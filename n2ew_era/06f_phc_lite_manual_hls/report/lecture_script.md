## 開場（約 2 分鐘）

**「這個專案做的事情，用一句話說：把一個能預測市場走勢的神經網路，從電腦軟體移植到一塊 FPGA 晶片上跑，並且驗證它在硬體上的結果和軟體上一樣。」**

（停頓一下，讓教授消化）

**「為什麼要這樣做？因為在高頻交易裡，速度就是錢。CPU 跑神經網路的時間不穩定——平均 117 微秒，但偶爾會突然跳到 780 微秒，那一次延遲就可能錯失一個交易機會。FPGA 不一樣，它每次都精確地跑完 83 微秒，沒有任何抖動。」**

---

## 第一段：背景（約 5 分鐘）

### 高頻交易是什麼

**「我先從為什麼高頻交易需要這麼快說起。」**

（講慢一點）**「傳統交易，人看行情、分析、下單，幾秒鐘到幾分鐘。高頻交易讓機器在『一眨眼』——大概 10 到 100 微秒——就完成這整個流程。1 微秒等於百萬分之一秒。在電腦速度這麼快的今天，為什麼還要這麼斤斤計較？因為如果你比競爭對手慢 1 微秒，你的訂單到達交易所的時候，好的價格可能已經被人家搶走了。所以延遲越低、越穩定，策略才越有效。」**

### FPGA 是什麼

**「CPU、GPU 大家比較熟。FPGA 是『現場可程式化閘陣列』，白話說就是一塊可以被重新佈線的晶片。你可以把它想成一塊可以無限次改寫的積體電路。」**

**「為什麼不用 GPU？GPU 很適合做大矩陣運算，但它的設計是為了 batch 處理——一次算幾百個樣本。如果你只有一個樣本要算（HFT 的情境），GPU 的延遲反而比 CPU 還高，而且也有 jitter 問題。FPGA 不同，沒有作業系統、沒有 Python、沒有垃圾回收——訊號進來，電路算完，訊號出去，每次都一模一樣。」**

---

❓ **教授可能問：「FPGA 比 CPU 快多少？」**

✅ **「從數字來看，平均延遲 83 µs vs CPU 117 µs，快了 1.4 倍。但更重要的是尾端延遲：CPU 的 p99 是 779 µs，也就是每 100 次執行就有一次超過 779 µs。FPGA 不論哪次執行都是精確的 83 µs。在 HFT 場景，那個偶爾冒出來的 779 µs 等同於錯失機會，所以確定性比平均值更重要。」**

---

## 第二段：模型架構（約 8 分鐘）

### PHC-lite 是什麼

**「接下來說我們在 FPGA 上跑的是什麼模型。」**

**「PHC-lite 是一個帶記憶的神經網路——專業術語叫 recurrent neural network。它的特別之處在於：它不只看現在的市場數據，還記得過去的狀態。每一步計算完之後，它會輸出一個『隱藏狀態』，然後把這個狀態傳給下一步用。這樣一來，模型就能融合歷史走勢做預測。」**

（指著計算流程表）**「它的計算分 9 個步驟。我用白話解釋幾個關鍵的：」**

**「Step 1：把當前市場特徵 x_t，做一次線性變換（就是矩陣乘法加偏置），再過一個激活函數，得到 encoded 特徵。這相當於把原始市場數據投影到模型理解的空間。」**

**「Step 2 和 Step 3：計算兩個控制訊號——gate（遺忘閘）和 candidate（候選記憶）。gate 決定舊記憶要保留多少，candidate 是這個時步想寫入的新資訊。」**

**「Step 4：更新記憶。用一個公式：新狀態 = DECAY × 舊狀態 + gate × candidate。DECAY 是一個學來的衰減係數，讓模型自己學到哪些過去資訊需要保留多久。」**

**「步驟 5 到 7 是一個增益機制，讓狀態之間有更複雜的互動，這是 PHC 系列模型的特色。」**

**「最後 Step 8 和 9：做最終正規化，然後用一個 16→2 的線性層輸出預測訊號 readout[2]。這個 2 維訊號的正負方向代表買/賣傾向的強度。」**

---

❓ **教授可能問：「這個模型和 LSTM 有什麼差別？」**

✅ **「LSTM 也是一種 recurrent 網路，有 forget gate、input gate、output gate 三個門。PHC-lite 的結構不完全一樣，它的 gain 機制和 synapse 模組讓狀態間的互動更豐富，可以看成是 LSTM 的一種改進變體。兩者的核心思路都是用 gate 機制控制記憶的保留和更新，但 PHC-lite 多了一個 loop input 自迴路，能捕捉更高階的時序模式。」**

---

❓ **教授可能問：「為什麼用 16 維？可以更大嗎？」**

✅ **「16 維是專門為 xc7z020 這顆入門級 FPGA 設計的。這顆晶片只有 220 個硬體乘法器（DSP48E1）。一個 16×16 的矩陣乘法，如果完全並行需要 256 個乘法器，已經超過晶片上限。如果改用 32 維，矩陣是 32×32 = 1024 個乘法器，完全不可能放進這顆晶片。16 維是在這個硬體限制下，能保持模型有一定表達能力的選擇。」**

---

## 第三段：工具鏈（約 5 分鐘）

### HLS 是什麼

**「FPGA 的傳統設計方式是寫 Verilog 或 VHDL——那是一種直接描述電路連接的語言，非常難寫也難除錯。HLS 讓工程師可以用 C++ 描述計算邏輯，工具自動把它轉成硬體電路。你可以把 HLS 想成 C++ 到硬體的編譯器。」**

### 為什麼選手動 HLS 而不是 hls4ml

**「市面上有個叫 hls4ml 的工具可以直接把 PyTorch 模型自動轉成 HLS，非常方便。但它有個問題：預設會把所有迴圈展開（unroll）來追求最低延遲，代價是資源用量極高。」**

**「對 xc7z020 這種入門 FPGA 來說，hls4ml 的預設設定直接讓 DSP 超過 100%，無法放進晶片。手動 HLS 讓我能精確控制每一個 pragma，在延遲和資源之間做出明確的權衡。」**

### 為什麼用定點數

**「最後說一下為什麼不用 float（浮點數）。HLS 工具如果看到標準的 tanh() 函數，會呼叫 Xilinx 內建的雙精度浮點 IP 核心——一個核心就要 2000 多個 DSP，我們整顆晶片才 220 個，直接超標 10 倍。」**

**「定點數 ap_fixed<24,12> 代表 24 bit 裡有 12 bit 整數、12 bit 小數。一個定點數乘法對應一個 DSP48E1 硬體乘法器，非常高效。而且定點數的精度完全可預測，不像浮點有捨入誤差的不確定性。」**

---

❓ **教授可能問：「定點數精度夠嗎？」**

✅ **「我們有兩個層次的精度驗證。第一層，csim/cosim 結果顯示 max_abs_diff = 0.00725，遠低於我們設定的 tolerance = 1.0。第二層，我們做了 sign agreement 分析：在 25,600 個時步裡，有 16 個時步的 readout 方向（正/負）和 float32 不同，sign agreement 是 99.9375%。而且這 16 個時步的 float32 輸出本身的絕對值都小於 0.00054——代表模型在這些時步『自己也不確定』，這些異號情形不會影響有方向性的交易訊號。」**

---

## 第四段：優化歷程（約 10 分鐘，最重要的部分）

**「接下來是整個專案裡最有技術含量的部分：8 輪 pragma 優化。我先解釋背景，再逐輪說明。」**

### 背景：FPGA 的四種資源

**「xc7z020 有四種主要資源。LUT 是做邏輯運算的；FF 是儲存一個 bit 的暫存器；DSP48E1 是硬體乘法器，這是最稀缺的，只有 220 個；BRAM 是塊狀記憶體，有 280 個 18K 單元。DSP 是瓶頸——矩陣乘法需要大量乘法器。」**

### v1：初始（DSP 2636%）

**「一開始寫完 C++ 跑 HLS，DSP 用量是 2636%，可用量的 26 倍。問題來自一行標準 C 函數：tanh()。HLS 工具看到它，自動呼叫 Xilinx 的雙精度浮點 tanh IP 核心。一個 IP 核心就要 2048 個 DSP。我有好幾個地方用到 tanh，加起來超過 5800 個 DSP。」**

**「修復：把所有 tanh 換成預計算的 65 點查表（TANH_LUT[65]），範圍 -4 到 +4，線性插值。這樣完全消除了浮點 IP 核心的呼叫。」**

### v2～v5：反覆無效（DSP 仍 1603%）

**「換了查表之後，DSP 從 2636% 降到 1603%，但還是超標太多。原因是矩陣乘法的迴圈被 PIPELINE pragma 強制展開。」**

（放慢速度）**「這邊有一個很重要的工具行為，我需要解釋清楚。」**

**「我在每個矩陣乘法函式上加了 #pragma HLS PIPELINE II=1，本意是讓計算流水線化，提升吞吐率。但工具有一個行為：只要看到 PIPELINE pragma，不管 II 值是多少，都會強制把所有 inner loop 完全展開（complete unroll）。這出現在編譯 log 裡的 WARNING [HLS 214-275]。」**

**「我試了三個方法想繞過這個行為：v3 移除 inner loop 的 UNROLL pragma、v4 改變陣列 partition 方式、v5 把 II 改成 297（每 297 個週期進一個輸入）。全部無效。因為不是 II 值的問題，而是 PIPELINE pragma 的存在本身就觸發了這個行為。解法不是調整參數，而是刪掉 PIPELINE pragma。」**

### v6：刪除 PIPELINE（DSP 247%）

**「刪掉所有 PIPELINE pragma，DSP 從 1603% 降到 247%。這是一個突破性的進展，代表方向對了。但還是超標，繼續找原因。」**

### v7：pipeline_loops 自動接管（DSP 121%）

**「v7 移除了所有陣列 partition pragma，但 DSP 只降到 121%，還是超標。這次的問題更隱蔽。」**

**「Vitis HLS 有一個全域設定叫 pipeline_loops——它會自動尋找迴圈次數小於某個閾值的迴圈，自動加上 PIPELINE。因為我的矩陣乘法 outer loop 只有 16 次，觸發了 pipeline_loops 的自動條件，出現了 INFO [HLS 214-376]——工具自己加上 PIPELINE。然後這個自動 PIPELINE 又觸發了上面說的 [HLS 214-275]，inner loop 再次被完全展開。接著展開後的索引變成常數，工具又自動 partition weight 陣列，出現 INFO [HLS 214-449]。」**

**「我把這叫做『三連鎖』：自動 pipeline → 強制展開 → 自動 partition。移除手動 pragma 完全沒用，因為工具主動替我加回來。」**

### v8：PIPELINE off（最終，DSP 21%）

**「解決方案非常乾淨：#pragma HLS PIPELINE off。這個 off 關鍵字的優先級高於 pipeline_loops 全域設定，明確告訴工具『不要對這個 loop 做任何 pipeline 優化』。三連鎖全部斷開，DSP 降到 21%，四種資源全部在預算內。」**

（停頓）**「從 2636% 到 21%，花了 8 輪，根本原因只有兩個：浮點 tanh（v1），以及 PIPELINE pragma 的級聯展開效應（v2~v7）。」**

---

❓ **教授可能問：「這樣不用 PIPELINE，latency 不會很高嗎？」**

✅ **「會的，這就是我們設計上的 tradeoff。序列執行讓 latency 是 8316 個時脈週期，也就是 83 µs。如果用 PIPELINE，latency 理論上可以降到 100 個週期以內（< 1 µs），但 DSP 會超標 7 到 16 倍，根本放不進 xc7z020。在這個晶片上，序列計算是讓設計可行的唯一選擇。如果換到 Alveo U50（5952 個 DSP），才有辦法全面 pipeline，latency 可以降到 5 µs 以下。」**

---

❓ **教授可能問：「8316 cycles 是怎麼算出來的？」**

✅ **「主要貢獻來自 7 個 linear layer，每個 16×16 矩陣乘法需要 16 × 16 = 256 個 multiply-accumulate 操作，一個接一個算，外加 outer loop overhead，每個 linear layer 大約需要 1300 個週期。7 個 layer × ~1300 + LayerNorm（~145 × 2）+ activation（~177）+ element-wise 操作 = 大約 8316 週期。這個數字可以在 csynth report 的 sub-module latency breakdown 表裡逐一查到。」**

---

## 第五段：驗證結果（約 5 分鐘）

### 三層驗證鏈

**「驗證分三層：csim 驗證 C++ 邏輯，cosim 驗證 RTL 電路，P&R 驗證真實硬體佈局。就像軟體開發裡的 unit test、integration test、production deploy。」**

### csim / cosim 結果

**「csim 和 cosim 都在 25,600 個時步上跑過，都是零錯誤通過。最大誤差 0.00725。」**

**「有一個細節很重要：csim 和 cosim 的 max_abs_diff 完全相同，都是 0.00725275。這代表 RTL 電路和 C model 在每一個 bit 上完全一致，合成過程沒有引入任何額外的捨入誤差。這是定點數的優點——精度完全由位元寬決定，和軟體計算完全一樣。」**

### Sign Agreement

**「我們另外做了 sign agreement 分析。16 個時步有方向不一致，比率 0.0625%，sign agreement 99.9375%。重要的是，這 16 個時步的 float32 輸出絕對值都小於 0.00054，模型本身在這些時步幾乎沒有方向性意見——這些不是訊號翻轉，而是模型的『無意見區』。」**

---

## 第六段：硬體結果（約 5 分鐘）

### 資源（讀表）

（指著資源利用率表）**「最終 P&R 的實際資源利用率：DSP 21%、LUT 14%、FF 8%、BRAM 2%。四種資源都在 100% 以下，設計是可行的。」**

**「有一個容易讓人困惑的地方：csynth 估算 LUT 用量是 24,836（46%），但 P&R 實際只有 7,555（14%），降了 70%。為什麼？因為 csynth 只做排程，不做邏輯優化。Vivado synthesis 做了 LUT 合併、常數傳播、死碼消除，加上序列執行讓大量邏輯可以時間複用，不需要多份拷貝，所以 Vivado 的優化空間特別大。70% 的降幅是正常的，不是數字有問題。」**

### Timing（讀懂 WNS）

**「時序的數字是 WNS = +0.020 ns。WNS 是『最差的那條訊號路徑距離違規還剩多少時間』。正數代表通過，負數代表違規。我們的最慢路徑需要 9.980 ns，時脈週期是 10 ns，剩餘 0.020 ns。22,941 個 timing endpoint 全部通過，TNS = 0.」**

（重要）**「+0.020 ns 很薄。如果要部署到生產環境，建議降頻至 90 MHz，WNS 估計會增加到 +1.13 ns，達到工業慣例的 ≥ 1 ns 建議值。Latency 從 83.16 µs 增加到 92.4 µs，約 11% 的代價。」**

### 功耗

**「功耗：Total On-Chip Power 0.357W，Junction Temperature 29.1°C（室溫 25°C 下）。xc7z020 的 TDP 典型是 1.5W，我們只用了四分之一，熱餘量非常充足。」**

---

❓ **教授可能問：「WNS 只有 0.02 ns，這個設計可靠嗎？」**

✅ **「Vivado 使用 Slow Process Corner——最保守的製程、電壓、溫度條件下做 timing 分析。在最壞情況下 WNS 仍然為正，代表設計在這顆晶片的 Commercial Grade 規格範圍內是合法的。但你說得對，0.020 ns 的 margin 不夠充裕，生產建議降頻至 90 MHz 取得更大裕量。這是我們在報告限制部分明確聲明的一點。」**

---

❓ **教授可能問：「你有上板（hardware-in-the-loop）驗證嗎？」**

✅ **「沒有進行上板測試。我們的驗證鏈是 csim → cosim → P&R，這在學術 FPGA 設計報告中是被接受的完整流程。cosim 模擬的是 timing-accurate RTL，等同於在電路層面驗證。上板還需要額外的 PS-PL integration（ARM 核心到 PL 邏輯的 AXI 介面），需要額外的時間和工程工作量。如果有上板驗證，預計 latency 測量結果會與 csynth 的 83.16 µs 一致，因為 P&R 已確認 timing met。」**

---

## 第七段：效能比較（約 3 分鐘）

（指著 FPGA vs CPU 比較表）

**「最後說效能比較。FPGA 的優勢有兩個維度：」**

**「第一，tail latency（尾端延遲）。CPU p99 是 779 µs，FPGA 是 83 µs，改善 9.4 倍。這是 HFT 真正關心的數字——不是平均值，是最壞情況有多壞。」**

**「第二，確定性。FPGA 每次都是 83 µs，沒有抖動。CPU 的 p99/p1 的差距（779 µs vs 61 µs）大到一個數量級，這個不確定性在 HFT 裡是個嚴重問題。」**

**「需要誠實說明的是：83 µs 不滿足 HFT L1 的 < 10 µs 要求。這個專案展示的是在 xc7z020 這個學術板上的 FPGA 推論可行性，以及完整的 HLS 設計方法論。要達到 10 µs 以內需要更高階的硬體（如 Alveo U50）或更激進的量化（INT8）。」**

---

❓ **教授可能問：「CPU baseline 的 p99 高不高？可能是 Python 的問題？」**

✅ **「你說得對，779 µs 包含 Python runtime 開銷、作業系統排程、PyTorch overhead 等複合因素。如果用 LibTorch（C++ PyTorch）或 TorchScript，CPU p99 會更低。但我們選擇測量真實 Python 管線的延遲分布，因為在實際的 HFT 信號處理管線中，訊號處理通常就是 Python 環境的，這個數字反映的是真實部署情境，不只是純粹的模型推論時間。這個限制在報告的 CPU baseline 方法說明中有明確揭露。」**

---

## 結語（約 1 分鐘）

**「總結一下：我們在 xc7z020 上完成了 PHC-lite 的完整 FPGA 推論實作。從資源超標 26 倍到全部在預算內，經過 8 輪系統性調試，確認了 HLS PIPELINE pragma 觸發級聯展開的根本機制，以及 pipeline_loops 自動接管的三連鎖反應。驗證結果是 25,600 步全部通過，sign agreement 99.9375%，P&R timing met，功耗 0.357W。」**

**「未來的改進方向，如果要縮短延遲，有三個選項：INT16 量化估計可以到 25 µs、縮小 hidden dim 到 8 可以到 8 µs、換 Alveo U50 可以到 5 µs 以下。這些都是下一步的工作。」**

## 附錄：可能被追問的深入問題

### Q：LayerNorm 的 sqrt 是怎麼算的？

A：「在 HLS 的 csynth report 裡，你會看到一個叫 sqrt_fixed_49_25_s 的子模組，這是 HLS 自動把 ap_fixed 的 sqrt 運算合成的。我們的 LayerNorm 計算公式是 (x - mean) / sqrt(var + 1e-5)，其中 sqrt 的輸入是定點數。這個子模組的 latency 是 28 個週期，比較少，不是 bottleneck。它使用的是 digit-by-digit 的定點 sqrt 算法，不需要浮點 IP 核心。」

### Q：你怎麼選擇 ap_fixed<24,12> 的位元寬？

A：「24 bit 和 12/12 的分配是一個平衡點。整數部分 12 bit 可以表示 ±2048 的範圍，在市場特徵的典型值域內（通常在 ±10 以內）夠用。小數部分 12 bit 給出 1/4096 ≈ 0.000244 的精度，這比我們最後量測的 max_abs_diff 0.00725 更細，理論上足夠。比這更窄（如 16 bit）可能造成 LayerNorm 的 variance 計算溢位；比這更寬會增加 DSP 使用量（需要更寬的乘法器）。這個選擇有一定的 empirical 成分，更嚴謹的做法是做量化敏感性分析，這是 future work 的一部分。」

### Q：DECAY 參數是怎麼學的？有什麼物理意義？

A：「DECAY 是訓練時學出來的每個 hidden dim 的衰減係數，值域在 (0, 1) 之間（通過 Sigmoid 限制）。接近 1 的 DECAY 讓對應的 state 維度記住很久以前的訊息；接近 0 的讓它快速遺忘。這讓模型能自動學到『哪些市場模式需要長期記憶，哪些只需要短期參考』，是 PHC 系列模型相較於傳統 LSTM 的改進點之一。在 FPGA 上，DECAY 是預先訓練好的常數陣列，合成時被存進 ROM。」

### Q：ALPHA 呢？

A：「ALPHA 也是訓練學到的常數，控制 self-loop 的強度（loop_input = state + ALPHA ⊙ gain ⊙ message 裡的 ALPHA）。它決定了狀態更新裡自迴路訊息的貢獻比例。在報告中的表格，ALPHA 是一個 16 維的 per-channel 常數向量，和 DECAY 一樣在合成時被存進 ROM。」

### Q：25,600 個測試向量夠嗎？有 distribution shift 的問題嗎？

A：「25,600 步來自 200 個 validation sequence，每個 128 個 timestep。這是 validation split 的前 200 個樣本，是有代表性的子集，但不是完整的 validation set。邊緣案例（極端值、NaN 邊界）沒有單獨測試。Distribution shift 這個問題是有效的——測試向量來自和訓練數據相同分布，不代表在真實部署的市場環境下精度一樣穩健。要更嚴謹的話需要 out-of-distribution 測試，這是一個待補充的環節。」
